# Dockolate 模型识别层重构：一切规则进数据，用户可改、免重编译

> 用户令（2026-11-04）：**所有规则不能只针对本机现有的模型，必须对用户以后添加的任何模型成立；
> 分类定性、名称都应允许用户自定义，不要每次改规则都重新编译。**

## 一、必要性（现状实测出来的硬伤）

| # | 现状 | 实测后果 |
|---|---|---|
| 1 | 分类靠 `ModelClassifier` 里的四个硬编码词表（image/video/audio/embed 各一串） | `Wan2.2-Lightning-I2V-4step`（LoRA）、`ControlNetModel`、`mmproj` 视觉塔、`spkrec-ecapa` 说话人嵌入、`grounding-dino` 检测模型 全被当成「模型」各占一行；用户新加的模型只要不在词表里，一律落 `.chat` |
| 2 | 引擎族判定靠 `Recipe.matches()` 里的字符串互相包含 | `engine:"mlx-serve"` 的 H3 配方认领了 `engine:"MLX"` 的 Qwen3-VL 运行行（`"mlx-serve".contains("mlx")`），把判官的状态/内存写到 H3 卡上 —— 用户看到的「H3 自己跑起来了」 |
| 3 | 名称来源只有「目录名 / 引擎自报」，没有用户覆盖 | 同一个模型在不同目录下会显示成三个不同的名字；`SenseNova-6.8-Code2Video-GGUF 路` 这种截断没人能读 |
| 4 | 管理入口 id 是内部实现（`disk:<路径>` / `recipe:<id>` / `runtime:<port>:<name>`） | 文档承诺的 `recipe:<配方id>` 在“配方与磁盘条目合并成一张卡”时就失效（实测 `找不到条目：launch:recipe:code2video-q6`） |

关键前提已确认：**`LauncherConfig.load()` 每轮都从 `registry.json` 读盘，没有任何内存缓存**；
GUI 与 hub daemon 都是周期刷新，所以「改数据 = 引擎下一次刷新就生效」这条通路现成，只差把规则搬进数据。

## 二、目标

1. **零硬编码语义**：新模型（新引擎、新目录、新命名习惯）靠改 `registry.json` 就能被正确分类、命名、折叠，**不重编译**。
2. **用户可自定义**：分类（category）、角色（主模型 / 部件）、显示名（title）、别名（aliases）、是否隐藏，全部可在数据里按「名字 / 路径 / 引擎」匹配改写。
3. **内置默认仍可用**：没有配置时行为与今天一致（默认规则从数据文件加载，代码里只留一份兜底副本）。
4. **规则可测可查**：提供 `--explain=<路径或名字>` 打印「这条是怎么被判定成这个类别的、命中了哪条规则」，不用猜。

## 三、数据模型（registry.json 扩 schema，向后兼容）

```jsonc
{
  "schema": 2,                       // 递增；旧版无此字段按 1 处理
  "scanDirs": ["…/models"],

  // ① 引擎族：把「引擎自称」映射成族，族内才允许认领运行行
  "engineFamilies": {
    "mlx-serve":  ["mlx-serve", "mlxserve", "mlx_serve"],
    "mlx-vlm":    ["mlx_vlm.server", "mlx-vlm", "mlx_vlm"],
    "mlx-lm":     ["mlx_lm.server", "mlx-lm", "mlx_lm"],
    "llama.cpp":  ["llama-server", "llama.cpp", "llamacpp"],
    "splash":     ["splash"], "strata": ["strata"],
    "ollama":     ["ollama"], "comfyui": ["comfyui", "comfy"],
    "whisper":    ["whisper", "mlx-whisper", "mlx_whisper"]
  },

  // ② 分类规则：**有序**，先命中先赢；用户写的永远排在默认之前
  "classifyRules": [
    { "match": { "name": "*lora*" },                  "role": "part", "category": "part", "label": "LoRA" },
    { "match": { "name": "*controlnet*" },            "role": "part", "category": "part", "label": "ControlNet" },
    { "match": { "path": "*/*/mmproj*" },             "role": "part", "category": "part", "label": "视觉投影" },
    { "match": { "name": "*vision*tower*" },          "role": "part", "category": "part", "label": "视觉塔" },
    { "match": { "name": "*ecapa*", "path": "*speechbrain*" }, "category": "embedding" },
    { "match": { "name": "*grounding-dino*" },        "category": "part", "hidden": true },
    { "match": { "path": "*/ComfyUI/*" },             "category": "image" },
    { "match": { "name": "*wan2*" },                  "category": "video" }
  ],

  // ③ 名称与归属覆盖：按「路径或名字」把显示名、别名、是否隐藏钉死
  "modelOverrides": [
    { "match": { "path": "*/SenseNova-6.8-Code2Video-GGUF" },
      "title": "SenseNova 6.8 Code2Video（Q6_K）",
      "aliases": ["code2video", "c2v"],
      "category": "video", "media": "llama.cpp" },
    { "match": { "name": "*MiniMax-H3-REF2VA*" }, "title": "MiniMax H3 REF2VA（全参考 · 8bit）" }
  ],

  "defaults": { "useBuiltinClassify": true }   // false = 只用用户规则
}
```

匹配语法（够用且不引入 DSL）：

- `match.name` / `match.path`：大小写不敏感的**通配符**（`*` 任意串），命中即算；
- `match.engine`：值必须是 `engineFamilies` 的键（先归族再比），**禁止子串互相包含**；
- `match.role`：`main` / `part`；`match.port`：整数；
- 一条规则可写多项，**全部满足**才算命中（AND）。

## 四、判定优先级（写进文档，也写进 `--explain`）

```
1) modelOverrides（用户显式钉死的名字/类别/隐藏）
2) classifyRules（用户自定义，自上而下）
3) 配方声明（recipe.category / media / attachments）
4) 内置默认规则（内置 classifyRules 文本，同语法）
5) 兜底：.chat（主权重）/ .part（非主权重）
```

运行时行归属（这次幻影的根因）同样收严：

```
一个运行行只能被认领一次；认领条件按强度排序：
  A 端口相同（运行行端口 == 配方 port）            ← 最强，服务/引擎都适用
  B 路径相同（配方 path == 条目 diskPath，符号链接解引用后比较）
  C 名称相同（归一化后全等，或用户 aliases 命中）
  D 引擎族相同 **且** 名字/路径有交集
  ✗ 仅「引擎族相同但配方未声明端口」不再单独成立（今天就是这条把判官行错给了 H3）
```

## 五、管理入口 id 规范化（免背内部 id）

`--mgmt-action=<动作>:<目标>`，`<目标>` 依次尝试解析：

1. `recipe:<配方id>` —— 配方若已与磁盘条目合并，自动解析到宿主条目（修今天 Code2Video 拉不动）；
2. `disk:<路径>` / 绝对路径；
3. `runtime:<port>:<name>`；
4. `engine:<引擎名或族名>` —— 供 `stop:engine:Strata` 这类脚本用法；
5. 裸名字：按 title / aliases / 目录名归一化匹配，**唯一**才动手，歧义就报错并列出候选（不猜）。

## 八、风险与边界
- **规则写错会把模型藏起来**：因此 `hidden` 规则必须能在 GUI 里一键「显示全部」，且 `--doctor` 列出被隐藏的条目数与原因。
- **性能**：规则匹配是每个扫描单元几条通配符比较，扫描本身已是重活；不额外引入正则引擎。
- **兼容**：`registry.json` 不写新字段时行为与今天一致（schema 1 视作空规则集）。

## 十三、类型视觉进数据 + 半透明大水印（2026-11-04 用户追加）

用户验收了小徽标方案，并要求两件事：图标要大、要像水印铺在卡片底上；并且"类型 → 图标/配色"也要能自己改、不用重编译。

- **数据驱动**：registry.json 新增 `categoryVisuals`：
  ```jsonc
  "categoryVisuals": [
    { "category": "video", "symbol": "film", "color": "systemRed" }
  ]
  ```
  取值由 `ModelVisuals`（5 秒缓存）读 `ClassifyData.loadFromRegistry()`；写错的 symbol/颜色名回落内置配色，不会渲染成空白。
  允许的颜色名：blue/red/orange/yellow/green/mint/teal/cyan/purple/pink/indigo/brown/gray。
- **大水印**：卡片底层加 `watermark`（同一枚 SF Symbol，pointSize 96/紧凑 64，透明度 0.13/0.10，锚在右下角 108×108），
  内容压在水印之上。远看颜色 + 形状就能认出类型，近看仍是原来的小徽标 + 文字。
- 颜色语义未变：**卡片底色/边框 = 运行状态**，**水印与小徽标 = 类型**。

## 十四、引擎托盘（2026-11-04 用户裁定）

卡片按「能启动它的引擎」分组，引擎 = 托盘；每个托盘一组标题 + 一个卡片网格。

归属规则**只认事实、不推断**：① 配方声明的 `engine`；② 运行时引擎自报（`engineName`）；
③ 都没有 ⇒ 进「未绑定引擎」托盘（标题注明「没有配方，也就没有可启动它的引擎」）。

> 用户明确否掉了「按文件格式推断引擎」（gguf→llama.cpp 之类）的方案：宁可留一个诚实的
> 「未绑定引擎」托盘，也不要给出可能错的归属。若将来要加推断，应作为独立开关并标注「推断」。

托盘排序：含运行中模型的在前，其余按名字，「未绑定引擎」永远最后；标题带 `N 个 · 常驻 X GB`。

## 十五、排序（2026-11-04 用户裁定）

托盘与模型各一个下拉选择器，选择记进 UserDefaults（`dk.sortTrays` / `dk.sortModels`），重启保持。

- **托盘**：`调用次数`（默认）/ `名称`。引擎没有"大小"，所以不做大小排序；
  调用次数 = 该托盘内所有成员的累计调用次数之和。「未绑定引擎」永远垫底。
- **模型**：`调用次数`（默认）/ `名称` / `大小`（按估算内存降序）。

**调用次数是跨重启累计的**：引擎侧计数器在引擎重启后归零，所以实现里按「增量」累加进
`UserDefaults["dk.usageCounts"]`（key = 条目 id）；不这样做，排序会被每次重启切断，
多数模型恒为 0，默认排序等于失效。

> 未做：真正的「频率」（单位时间调用量）。它需要按时间窗口采样（例如最近 1 小时请求数），
> 目前只有累计量。若用户要，再加一个按小时桶的环形统计。

## 十六、托盘并排 + 内存池刻度归位（2026-11-04）

**① 托盘并排**：托盘不再一列到底。按列表宽度算列数 `columns = clamp(宽/470, 1, 3)`，
托盘先装进「标题 + 网格」的小栈，再按列宽切片成行，`NSStackView(distribution: .fillEqually)`，
末行用 `dkSpacer()` 补齐，避免被拉伸。列数进指纹 ⇒ 窗口改宽度后下一次刷新自动重排。

**② 刻度归位**：宽版布局原为 `[刻度][池外小箱 96][池子]`，视觉上刻度像是给池外小箱标的
（用户误读为"池外池也只有 整机容量"）。现改为 `[池外小箱][刻度][池子]`：
- 池外小箱挪到最左，宽度 **96 → 64**，高度 **与池子等高 → 0.58×池子**（矮一截，明显不是同一根轴）；
- 刻度列改为 `x = 池子左壁 − tickW`，紧贴池壁，与箱子之间留 10 pt 缝（`offBoxTickGap`）；
- 箱内标签因此收紧为「池外 / 未载 / NN GB」三行小字，量过宽度不溢出。

### 十六·补（托盘并排没生效的根因）

用户反馈「托盘并没有并列」。实测窗口 **796 × 1072 pt**（CGWindowList 读取），
原阈值 `470 pt/托盘` ⇒ `796/470 = 1` 列，永远排不出并排。另外 `catalogList.bounds.width`
在首次 build 时可能还是 0，也会退化成 1 列。

修法：宽度取 `max(catalogList 实测宽, 窗内容宽 − 80)`，阈值降到 **330 pt/托盘**
（`columns = clamp((宽+10)/340, 1, 3)`）。796 宽时 ⇒ 2 列。

排布自检：带 `DOCKOLATE_DEBUG_LAYOUT=1` 启动时把 `columns / listWidth / 托盘名`
写进 `/tmp/dockolate-layout.txt`（正式启动不写）。注意 GUI 的目录扫描是**开窗才跑**，
直接跑二进制不开窗不会产出该文件。

## 十七、引擎归属（2026-11-04 用户裁定）

用户指出：**ComfyUI 是引擎，不是模型**；Qwen-Image 2.1、Edit 2511 是跑在它上面的模型。
原先 ComfyUI 只是一张 `service` 卡片、引擎为空，生图权重则孤零零进了「未绑定引擎」托盘。

- `modelOverrides` 增加 **`assignedEngine`**：把磁盘上的模型挂到某个引擎托盘下，不需要为每个模型写启动配方。
  归属优先级：**配方 `engine` → `assignedEngine` → 运行时自报 → 「未绑定引擎」**。
- ComfyUI 配方（id `comfyui`）改为 `engine: "ComfyUI"`，于是它自己就是一个托盘；
  `Qwen-Image-2.1*` / `*Qwen-Image-Edit*` 两条覆盖把它们放进同一托盘（category=image, media=comfyui）。
- 通用性：任何用户加新模型都能这样挂——写一条覆盖即可，不用改代码、不用重编译。
- `--explain=<条目>` 现在会打印「归属引擎」，排查「为什么它在这个托盘里」不用猜。
