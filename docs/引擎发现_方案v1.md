# 引擎与权重发现：怎么才算「总是能正确」——方案 v1

> 状态：设计稿（未开发）。日期 2026-10-28。前一版事实基础：v1.2.0 的探测链路（见 `docs/开发文档.md §15`）。
> 本文回答一个问题：**换了机器、换了引擎版本、加了新权重之后，Dockolate 凭什么还能认对？**

---

## 0. 一分钟

「认出机内各种不同版本的模型」其实是**三个不同的问题**，混在一起谈就永远说不出「能不能保证」：

| # | 问题 | 现状 | 可保证程度 |
|---|---|---|---|
| A | **谁在跑**（进程 / 端口 / 引擎名 / 加载了哪个模型） | v1.2.0 已做 | 可以做到「不回归」——但要靠回归测试，不靠白名单 |
| B | **这是什么东西**（同一模型的哪个量化、主权重还是草稿/投影、多大） | 只拿了引擎自报的字符串 | 可以强保证：**内容嗅探**（GGUF/safetensors/config.json）比任何命名约定可靠 |
| C | **盘上有哪些版本**（引擎没登记、也没在跑的权重） | **完全没做** | 只能保证「已知仓库 + 用户声明的目录」全覆盖；任意目录无法保证（见 §10） |

结论先给：**「总是正确」不可能靠把引擎名单写全做到**——名单永远落后于版本。能做到的是三条：

1. **判据基于协议与内容，不基于名字**（§4）；
2. **每个「没找到」的结论都要两条独立证据**（§4 R2）——这一次的 bug 就是单条空数组就下了结论；
3. **认不出来的东西必须显式出现在界面上，并能一键导出证据**（§4 R6）——这样漏报是可发现的，而不是静默的。

## 1. 这次的 bug 说明了什么（不是「漏了一个引擎」）

v1.2.0 修的那处，根因不是「名单里少了一条」，而是三条**结构性**错误，形态会以别的样子再回来：

| 形态 | 后果 | 判据化后的规则 |
|---|---|---|
| 分支**按顺序 return**，先命中的赢 | 兼容层（半套 Ollama API）把真实状态盖住 | R1 按「信息量」选适配器，不按写完的先后 |
| 单个空数组当作**否定结论** | 「没有加载模型」 | R2 否定需两条独立证据 |
| 未知状态字符串**丢进兜底桶** | `state="ready"` 被当成未加载 | R3 未知状态原样透传并在界面显示 |

所以方案的第一原则是：**把判据从「谁的名字对上」改成「谁的载荷说得更清楚」**。

---

## 2. 已实测的事实（本机取样，具体路径与型号不入公开仓）

写方案前先量了三件事，避免在这里猜：

1. **GGUF 头部可读且信息够用**：魔数 `GGUF` → 版本 → 张量数 / KV 数 → KV 表里直接有 `general.architecture`、`general.name`、`general.size_label`、`general.license`；
   实测同一目录下「主权重 / 草稿（MTP）/ 视觉投影（mmproj）」三类文件在 KV 里的 `architecture` 就不同 ⇒ **不看文件名也能分清三类文件**。读取成本：只读头部几 KB，不用扫完 GB 级文件。
2. **safetensors 头部可读**：8 字节 LE 头长度 + JSON，`__metadata__.format` 给出 `mlx` / `pt` 之类，张量数可数 ⇒ 能区分「MLX 权重」与「PyTorch 权重」。
3. **`config.json` 是量化版本的权威来源**：`architectures` / `model_type` / `quantization{bits, group_size, mode}` 三项足以把「同一家族的 4bit / 8bit / IQ3 / IQ4」分开。
4. **反面事实（很重要）**：「从进程打开的文件反推权重」这条路**只在部分引擎上成立**。实测一个「按需加载、用完释放」的引擎，加载完成后只留 5 个 fd，**权重文件一个都不在**（权重读完即关）。
   ⇒ 打开的文件只能当**加分证据**（llama.cpp 这类常驻 mmap 的引擎很有效），不能当主干。

## 3. 为什么「名单写全」注定失败

- 引擎会改名、会 fork、会同时兼容多套 API（这一次就是「Ollama 兼容层 + 自有状态字段」）；
- 同一个产品的不同版本，同一个端点的**字段名会变**（`state: loaded` → `ready`）；
- 用户自己写的服务（一个 Flask 包一层 `llama.cpp`）永远不在名单里，但它完全可能是用户最常用的那个。

⇒ 名单可以留（用于**显示名**），但**不能当判据**。

## 4. 六条判据（写成可测的规则，不是口号）

| 编号 | 规则 | 怎么测 |
|---|---|---|
| **R1** | **载荷优先**：对同一端口，把各接口的响应都取到，按「信息量」打分（有逐模型状态 > 有常驻字节 > 只有 id 列表 > 空数组），取最高分者做适配器；平手才用端口/进程名兜底 | 给每个 fixture 断言「选中的适配器」与「解析出的状态集合」 |
| **R2** | **否定要两条证据**：任何「没有模型 / 没在跑」的判断，必须有两类独立证据同时为否（例如 `/v1/models` 全部非常驻 **且** `/api/ps` 为空 **且** 进程内无权重 fd 打开）。只有一条时显示「疑似未加载（证据不足）」，并把证据写进 tooltip | 构造「/api/ps 空但 /v1/models 有 ready」的 fixture，断言不得判为「未加载」 |
| **R3** | **未知状态透传**：状态字符串先查映射表（`ready/loaded/running` → 已加载；`loading/unloading` → 加载中；`error/failed` → 故障），查不到就**原样显示**「引擎自报：`<原文>`」，不并入「未加载」 | fixture 喂一个 `state="warmup2"`，断言界面出现原文 |
| **R4** | **三层证据交叉，缺层不丢行**：进程（argv / 路径 / 打开的 fd）→ 监听端口（含 Unix domain socket）→ 协议载荷。任一层独有发现的东西**都要出现在界面上**（可能标为「待确认」），不得因为另一层没有就丢弃 | 起一个只监听 UDS 的假引擎，断言仍被列出 |
| **R5** | **身份双源**：模型身份 = 引擎自报 id（`org/model` 保留前缀）× 内容嗅探（`config.json` / GGUF 头 / safetensors 头）。去重按 `realpath + inode`（符号链接与硬链不算两个），展示按 `家族 + 量化` 分组 | 同一权重建两个软链，断言只出现一次；同一家族 4bit/8bit 各一行 |
| **R6** | **未知即显式**：任何一个「看起来像模型服务但不是已知适配器」的进程/端口，必须在界面上占一行「未识别的引擎：<进程名> <端口>」，并提供「导出发现报告」；任何「盘上有但没有任何引擎登记」的权重目录，也必须占一行「在盘、无引擎登记」 | 起一个假服务回 200 但载荷形状未知，断言出现该行且报告能导出 |

**R1 的信息量评分（草案）**——分数只用来排序，不参与判定：

```
+3  每条模型记录里有 逐条状态（state/loaded 任一）
+2  有每模型常驻字节（bytes_resident）
+2  有磁盘字节或量化字段（bytes_on_disk / quantization）
+1  data[] 非空
+1  响应里带服务自报名（owned_by / server / version）
 0  空数组（只能证明「这个接口此刻没东西」，不能证明「没有模型」）
```

## 5. 三层架构

```
                     ┌──────────────────────────── 显示层 ────────────────────────────┐
                     │ 正在运行 / 挂载待机 / 加载中 / 故障 / 在盘未登记 / 未识别（待确认） │
                     └───────▲─────────────────▲──────────────────▲──────────────────┘
             ┌───────────────┴──┐   ┌──────────┴────────┐  ┌──────┴─────────────────┐
             │ ① 运行时层(已有)  │   │ ② 身份层(新)       │  │ ③ 清单层(新)            │
             │ 进程 / 端口 / 载荷│   │ 内容嗅探 + 去重    │  │ 磁盘仓库扫描 + 三方对账  │
             └──────────────────┘   └───────────────────┘  └────────────────────────┘
```

**① 运行时层**：v1.2.0 已有，按 R1/R2/R3 改造适配器选择与否定判定；补 UDS 监听、补 `--probe <port>` 输出原始载荷供用户反馈。

**② 身份层**：把「引擎说它叫什么」升级成「它说叫什么 + 文件里写的是什么」。规则：

- 目录型权重（`config.json` + `*.safetensors`）：`architectures` / `model_type` / `quantization{bits,group_size}` → `家族 · 量化 · 参数量（若可得）`；
- 单文件权重（`*.gguf`）：GGUF KV 的 `architecture` / `name` / `size_label` → 同上，并识别**文件角色**（主权重 / 草稿 MTP / 视觉投影 mmproj / LoRA）；
- 只读头部（前 ~64 KB），**不扫全文件**；结果按 `(realpath, size, mtime)` 缓存，避免每次轮询重读。

**③ 清单层**：把「盘上有」这件事本身变成一等公民。

扫描根（默认，全部只读）：
1. Hugging Face 缓存（`models--<org>--<name>` 目录名本身就是 repo id，和引擎自报 id 天然对得上）；
2. Ollama 的 manifests / blobs（有清单即可读家族 + 量化 tag）；
3. LM Studio 的 `models/<publisher>/<repo>/`；
4. ComfyUI 的 `models/{checkpoints,unet,diffusion_models,loras,vae,text_encoders}`；
5. 用户声明目录（`engines.json` 新增 `modelDirs`，可在界面里「添加模型目录」）。

对账（三方）：
- 引擎自报 id ↔ 嗅探出的身份 ↔ 盘上目录 三者做链接；
- 只在引擎出现 → 行来自运行时层；
- 只在盘上出现 → 行标「在盘、无引擎登记」，tooltip 给出可复制的「怎么让它跑起来」（说明该引擎怎么登记，不猜命令行）；
- 冲突（引擎说 A、文件写 B）→ 两个都显示，标「引擎自报 A / 文件写 B」，因为这通常意味着引擎加载了缓存副本或软链。

## 6. 让「以后也不会坏」的机制

这三条才是「总是」的来源，不是代码量：

1. **签名表外置成资源 JSON**：适配器识别不写死在二进制里，`adapters.json` 随应用发布（版本号 + 载荷特征 → 适配器 id）。新引擎上线可以先发一个 JSON，不必等用户升级应用。用户本地可覆盖。
2. **fixture 回放测试**：把每种引擎/版本的响应体录成 fixture（脱敏），单元测试断言「选中的适配器 + 解析出的状态集合 + 是否判为未加载」。新增一种引擎 = 加一个 fixture，**回归由测试保证**，而不是由人记得。
3. **`--discovery-report`（脱敏 JSON）**：一次性导出「扫了哪些端口、每个端口原始响应的**形状摘要**（键名、类型、条数，不含值）、选中的适配器与分数、进程识别结果」。用户反馈 bug 时贴这个，维护者 5 分钟就能加一个 fixture。文档里写清脱敏口径（不导出模型路径、不导出提示词、不导出任何 key）。

## 7. 显示口径（「正确显示」的定义）

| 列 | 规则 |
|---|---|
| 名字 | 引擎自报优先；没有就用嗅探身份（`家族 · 量化`）；都没有就 `文件名(去扩展名)`。**仓库式 id 保留 `org/` 前缀** |
| 状态 | 正在运行 / 挂载待机 / 加载中 / 出现故障 / 在盘未登记 / 未识别（待确认）。未知状态字符串原样显示 |
| 内存 | 服务自报常驻字节优先；否则进程 `phys_footprint`（多模型同进程时注明是合计） |
| 版本区分 | 同一家族多量化各占一行，行内写 `bits / group_size / 文件大小`；**同名不同路径**按 `realpath` 视为两个 |
| 置信度 | 每行三档：确定 / 推测 / 待确认。推测与待确认必须能在 tooltip 里看到依据（例如「端口在、载荷形状未知」「引擎自报 id 与文件头不一致」） |

## 10. 「总是」到这里为止：能保证与不能保证

**能保证**（有测试兜着）：

- 已覆盖引擎的**任何子集组合**（多引擎并存、同进程多模型、只有 UDS、只有非默认端口）都能列出；
- 引擎报「加载中 / 未知状态」时**不会**被显示成「没加载」；
- 同一权重被软链多份时不会重复计数；同一家族多量化能被分开；
- 认不出来的东西**一定出现在界面上**，且能一键导出证据。

**不能保证**（必须写进 README，避免过度承诺）：

- **任意目录**下的权重都能被发现——只扫已知仓库 + 用户声明的目录。全盘扫描既慢又涉隐私，不做。
- **容器内**引擎：进程在宿主不可见，只能靠端口 + 载荷（端口映射到别处时无法发现）。
- **别的用户**启动的进程：读不到 fd / 路径（权限），只能靠端口。
- 全新协议（非 HTTP、非 OpenAI 兼容、无 `state` 字段）的引擎首次出现时，只能落进「未识别（待确认）」——**直到有人提交一次报告**。

这条边界本身就是设计的一部分：**把「不知道」做成可见状态，而不是猜一个答案。**

## 11. 待确认

1. 清单层是否要扫「应用容器内的模型」（LM Studio / Ollama 的 GUI 版模型目录）——涉及沙盒路径，需实测一台装了它们的机器。
2. `modelDirs` 的默认值：是否默认附加当前用户的模型目录们（会导致首启 1–2 秒磁盘 IO），还是首次运行时问一次。
3. 每行要显示到什么粒度：`家族 · 量化 · 大小` 够不够，还是需要参数量与上下文长度（需读 GGUF 更多 KV）。
4. 「在盘、无引擎登记」这一行是否要提供「怎么跑起来」的固定文案（各引擎命令不同，容易被当成承诺）。
