# Dockolate 开发文档

> 在 macOS Dock 图标上实时显示 CPU / GPU / 内存占用率，点图标可看三榜进程排行。
> 最后更新：2026-10-14（v2）

---

## 1. 项目定位

用户愿望：**一个常驻 Dock 栏的图标，以实时动画显示 CPU、GPU、内存占用率**；
v2 追加：数字要更大、点图标要能看到占用最高的三个进程。

技术前提（已核实）：macOS 的 **Dock 图标不能承载文字流**，它是应用图标位图，只能整张替换。
因此「实时数字」有两条路：

1. 菜单栏 status item —— 可以放文字，但不在 Dock；
2. Dock 图标动态重绘 —— 每次把当前读数画成一张新位图，`NSApplication.applicationIconImage` 换上。

主视觉走 **Dock 图标**；菜单栏读数保留但**默认关闭**（v2 要求），窗口里的开关可随时打开。

---

## 2. 技术选型

| 决策 | 选择 | 理由 |
|---|---|---|
| 语言 | Swift + AppKit | 系统原生，零第三方依赖 |
| 构建 | `swiftc` 直接编 `main.swift` 成 .app bundle | 不用 Xcode 工程；`build.sh` 一条命令出包 |
| 采样 | Mach / IOKit 公开接口 | 无 root、无私有 API |
| GPU（系统级） | `ioreg -c IOAccelerator` → `Device Utilization %` | macOS 无公开 GPU 占用率 API；`powermetrics` 要 root |
| GPU（按进程） | `ioreg -c AGXDeviceUserClient` → `AppUsage.accumulatedGPUTime` | **见第 4 节，v2 的关键发现** |
| 常驻 | LaunchAgent（`RunAtLoad` + `KeepAlive`） | 登录自启 + 崩溃自拉起；`Aqua` 会话内运行才有 Dock 图标 |

参考过的现成方案（确认路线可行，未抄代码）：`exelban/stats`、`hakaru/MacSlowCooker`（Dock 图标显示 GPU）、MacVitals（IOKit 读 GPU）。

## 3. 架构

单文件 `src/main.swift`：

```
采样层    CPUSampler / MemorySampler / GPUSampler        ← 系统级三项
          ProcessSampler                                 ← 按进程三榜
模型      Sample { cpu, gpu?, memPct, memUsedGB, memTotalGB }
          ProcStat { pid, name, value }
渲染层    makeDockIcon(s) → NSImage(256×256)             ← 纯函数，给定数值出图
展示层    StatusItemController（菜单栏，默认隐藏）
          ProcessWindowController（进程排行窗口）
驱动      AppDelegate：1s 采样 Timer + 0.5s 插值 Timer
```

**采样与渲染解耦**：`makeDockIcon` 是纯函数，因此 `--dump --mock=...` 可脱离 GUI 验收任意数值的成图。

## 4. 数据口径（重要，别记错）

### 系统级三项

| 指标 | API | 算法 | 已知偏差 |
|---|---|---|---|
| CPU | `host_processor_info(PROCESSOR_CPU_LOAD_INFO)` | 全核 Σ(user+system+nice) / Σ(全部) 的**两次采样增量比** | 首拍无基准 → 返回 nil |
| GPU | `ioreg -c AGXDeviceUserClient` → Σ`accumulatedGPUTime` 增量 | 所有客户端 GPU 时间总和 ÷ 墙钟 | **不要用 `Device Utilization %`，见下** |
| 内存 | `host_statistics64(HOST_VM_INFO64)` | (**internal** + wire + compressor) × pageSize ÷ hw.memsize | **不要用 active_count，见下** |

页面大小走 `host_page_size()` 实取（本机 16384），不写死 4096。

#### 两个踩过的口径大坑（v2.2 修正，用户当面抓出来的）

**① 内存不能用 `active_count`。**
`active_count` 里混着大量 **file-backed 页面**（文件缓存）。macOS 会把空闲内存全用来做缓存，
本机实测：应用匿名内存只有 **8.8 GB**，而外部文件缓存 **52.5 GB**、压缩器 **26.9 GB**、wired **6.0 GB**。
用 `active + wired + compressor` 会算出 62 GB（64%），把 52 GB 缓存错算成「已用」，**虚高 20 GB**。
正解：`internal_page_count`（匿名页）+ `wire_count` + `compressor_page_count` = 41.6 GB（43%），
这才是「活动监视器」的 Memory Used 口径。

**② GPU 不能用 `IOAccelerator` 的 `Device Utilization %`。**
实测该字段**会假报 0**：Metal 满载压测期间仍偶有采样读出 0，低负载时长期为 0
（同期 per-process 明明有 7%+ 的 GPU 时间）。用户会立刻发现「明明是 0，不对吧」。
正解：Σ 所有 `AGXDeviceUserClient` 的 `accumulatedGPUTime` 增量 ÷ 墙钟。
对照实测：client 总和 96.5%，同期 `Device Utilization %` 83–90% 且中途漏出一次 0。

> 顺带记：`top -l 1` 的 `PhysMem: 94G used` 是把文件缓存也算进去的口径，与活动监视器不同。
> 用户说「内存快顶满」时，先分清他说的是哪个口径，别急着说「没满」。

### 按进程三项（v2 新增）

| 指标 | 来源 | 说明 |
|---|---|---|
| CPU | `ps -A -o pid=,pcpu=,comm= -r` | `-r` 按 CPU 降序 |
| 内存 | **`proc_pid_rusage` → `ri_phys_footprint`**（libproc） | 物理占用，与活动监视器同口径。**不要用 `ps` 的 rss，见下** |
| GPU | `ioreg -r -c AGXDeviceUserClient -l -w 0` | **见下** |

**按进程 GPU 是本次的关键发现。** macOS 没有公开的 per-process GPU 占用 API
（`powermetrics` 要 root，Activity Monitor 用私有接口），但 IOKit 里每个
`AGXDeviceUserClient` 实例：

- `IOUserClientCreator` = `"pid <N>, <进程名>"` —— **直接给出持有进程**；
- `AppUsage` 数组里的 `accumulatedGPUTime` —— 该客户端累计 GPU 时间（**纳秒**）。

两次采样求差 ÷ 墙钟，即「该进程占用了多少颗整 GPU 的算力」。

实测校验（M5 Ultra）：

| 场景 | 榜首 | 数值 | 同期 `Device Utilization %` |
|---|---|---|---|
| 空载 | WindowServer | 10.1% | 0–10% |
| Metal 满载压测 | gpustress | 87.4% / 92.9% | 85–89% |

两者量级吻合 ⇒ 口径正确。

**注意**：WindowServer 常年占据榜首（它代为合成所有窗口），这不是 bug。

#### ③ 进程内存不能用 `ps` 的 rss（v3.1 修正，用户第二次抓出来的）

用户质疑「应用内存 29.3 GB，可前三名加起来才 2 GB」，一查果然是 `ps` 在撒谎：

| 进程 | `ps ... rss` | `top` / `phys_footprint` |
|---|---|---|
| Python (main.py) | 0.97 GB | **22.97 GB** |
| python3.11 (omlx-server) | 几乎不显示 | **18.13 GB** |
| Hermes Helper | 1.05 GB | 1.19 GB |

`ps` 的 rss 对 mmap 大户**少报一个数量级**（23 倍）。正解是 libproc 的物理占用：

```swift
var pids = [pid_t](repeating: 0, count: 8192)
let bytes = proc_listpids(UInt32(PROC_ALL_PIDS), 0, &pids,
                          Int32(pids.count * MemoryLayout<pid_t>.stride))
var info = rusage_info_current()
withUnsafeMutablePointer(to: &info) { p in
    p.withMemoryRebound(to: rusage_info_t?.self, capacity: 1) { rp in
        proc_pid_rusage(pid, RUSAGE_INFO_CURRENT, rp)   // ri_phys_footprint
    }
}
```

遍历约 780 个进程耗时 < 100 ms，比 `top -l 1`（要 0.5–1 s，还会卡住主线程）划算得多。
改完后与 `top` 逐项吻合（22.97 vs 23G、18.13 vs 18G）。

> **注意**：`phys_footprint` 含共享页，各进程相加（约 53 GB）会**大于**系统口径的应用内存（29.3 GB），
> 这是重复计算导致的正常现象，UI 上必须注明「含共享页」，否则用户会问「怎么比总量还大」。

### 换页（swap）—— 只在窗口显示，图标不显示

来源 `sysctl -n vm.swapusage`，解析 `total = …M  used = …M`，按 M/G/K 换算成 GB。

用户明确定过：**压缩内存与换页不进 Dock 图标**（图标只给一个总占用百分比，一眼看状态），
只在窗口的明细行里列出。窗口每行分工：

| 行 | 内容 |
|---|---|
| 总览 | CPU / GPU / 内存 已用÷总量（百分比） |
| 内存去向 | 应用 + 内核联动 + 压缩 = 已用 ｜ 文件缓存（可回收）｜ 空闲 |
| 换页 | 已换页 ÷ 上限（`vm.swapusage`） |

这两个明细行存在的意义就是回答同一个问题：**为什么进程榜加起来才几个 GB**。

## 5. 渲染规格（v3：水位四宫格）

### 为什么不用数字

用户 v3 的判断：**图标里不需要数字**。理由是数字会和字母水印抢空间，而 Dock 图标本来就看不清精确数值。
改成「水位」后：

- 字母可以占满整格，一眼认出是什么指标；
- 水位高低提供的是**相对紧迫感**，比一个需要凑近读的数字更有用；
- 精确数值去窗口里看。

### 布局：2×2 四宫格

```
┌────────┬────────┐
│   C    │   G    │   左上 CPU    右上 GPU
│  ▓▓░░  │  ▓░░░  │
├────────┼────────┤
│   M    │   Z    │   左下 内存   右下 压缩+换页
│  ▓▓▓░  │  ▓▓▓▓  │
└────────┴────────┘
```

- 画布 256×256；`margin=24`、`gap=12`；四格各 98×98 正方形。
- 每格：深色槽底 → 底部往上填充水位（`alpha 0.92`，裁到圆角内）→ 水面高光线 1.5px → 大号白字母水印 → 圆角描边。

**v4 调整：M 与 Z 换位**（用户要求「看起来更舒服」）。换后阅读顺序是
C → G → M（用量）→ Z（挤压程度）：上排算力、下排内存，M 在前 Z 在后，
与菜单栏读数 `C / G / M`、窗口里 M 概要行 → Z 明细行一致。
Z 是 M 的补充指标，放在最后一格最不打断主线。

### 字母与含义

| 字母 | 位置 | 含义 | 计算 |
|---|---|---|---|
| **C** | 左上 | CPU 占用 | 全核增量比 |
| **G** | 右上 | GPU 占用 | Σ GPU 客户端时间增量 ÷ 墙钟 |
| **M** | 左下 | 内存占用 | (应用 + 联动 + 压缩) ÷ 物理内存 |
| **Z** | 右下 | **内存压缩 + 换页水位** | (压缩内存 + 已换页) ÷ 物理内存 |

**Z 的口径**：`(compressor_page_count × pageSize + vm.swapusage.used) / hw.memsize`。
它回答的是「系统为了腾地方，把多大比例的物理内存压起来或挪到磁盘了」——
0% 表示宽松，越高表示内存越紧张。与 M 是两个维度：M 看「用了多少」，Z 看「被挤压了多少」。

### 水位配色（四档）

| 水位 | 颜色 |
|---|---|
| < 20% | 蓝 `(0.32,0.62,0.98)` · 极低 |
| 20–50% | 绿 `(0.30,0.80,0.42)` · 低 |
| 50–80% | 黄 `(0.98,0.75,0.20)` · 中 |
| ≥ 80% | 红 `(0.95,0.32,0.28)` · 高 |

### 字母可读性（踩过的坑）

- 字母画在**水位之上**（不是水位之下），否则高水位时字母被淹掉；
- 纯白字压在高饱和彩色上会「糊」进底色（实测 M 在绿水位上对比度偏弱），
  所以加 **`strokeColor` 极淡黑 + `strokeWidth = -2.5`** 描边把字母钉住；
- 字母字号取格高 ×0.92 并裁到格内：再大就会上下被切得认不出（`C` 会变成 `O`）。

## 6. 本机 AI 模型一栏（v4）

> 文中出现的端口都是各家引擎的**默认值**，只用来说明内置兜底表长什么样。
> 实际探测以「被识别为模型服务的进程实际监听了哪些端口」为准，
> 换端口照样能认；用户也可以用 `engines.json` 显式声明。
> 面向用户的 README 与 Release notes 里不列端口，避免给不同环境的用户造成误导。

窗口里除三段进程榜外，新增一段：**内存里挂着的本地 AI 模型 + 各自状态**，按内存占用降序。

### 为什么需要两路数据

| 只看进程 | 只看网关 |
|---|---|
| 认不出模型名（oMLX 把自己的 argv 改写成 `omlx-server`，进程名只剩 `python3.11`）；也不知道「本该有哪几个模型」 | 只反映配置声明，服务崩了照样标 resident，看不出真假 |

所以交叉两路：

1. **进程侧（libproc）**：谁真的占着内存（`proc_pid_rusage` 的 `ri_phys_footprint`）、
   监听哪个端口（fd 扫描）、有没有在算（CPU / GPU 时间增量）；
2. **网关侧（`127.0.0.1:8010/v1/models`）**：本机声明了哪几个模型、
   哪个 `resident`、各自落在哪个端口。

网关连不上时（`gatewayUp=false`）只列已加载的进程，并在脚注里说明。

### 状态口径（三态 + 未加载）

| 显示 | 判据 |
|---|---|
| **正在运行** | 进程在、端口在监听、**最近 12 秒内算过东西**（2 秒窗口内 CPU 或 GPU 时间增量 ≥ 30 ms） |
| **挂载待机** | 进程在、端口在监听、这段时间没有计算 —— 权重仍占着内存 |
| **出现故障** | 网关声明为常驻但端口连不上；或进程在、有端口却不监听（半死） |
| 未加载（脚注） | 网关声明存在但 `resident=false`，不占内存，单独一行列出、不参与排序 |

无服务端口的引擎（Draw Things 这类应用内模型）不判故障，只按活动分「运行 / 待机」。

### 引擎识别

`kind` 关键字表覆盖：oMLX / llama.cpp / MLX(lm/vlm) / Ollama / LM Studio / vLLM / SGLang，
以及生图与视频：**ComfyUI** / Draw Things / mflux / Fooocus / InvokeAI / sd.cpp / A1111 / Diffusers / Qwen-Image / Flux。

兜底两招（实测必需）：

- **端口推断**：`8188 → ComfyUI`、`7860 → Draw Things / A1111`、`8888 → Fooocus`、`9090 → InvokeAI`。
  ComfyUI 的进程叫 `Python`、argv 只有 `main.py --listen 127.0.0.1 --port 8188`，
  名字和参数里都没有 "comfy" 字样，只能靠端口认；
- **内存门槛只对无端口进程生效**：有监听端口的服务一律收（ComfyUI 主进程 RSS 只有 62 MB，
  权重全在 mmap/GPU 里），无端口的应用要求 footprint > 300 MB，避免把客户端壳子算进来。

### ComfyUI 显示真实模型名

只写「ComfyUI」说不清它此刻在跑什么。ComfyUI 没有「当前加载了哪个 checkpoint」的接口，但：

- `GET /queue` —— 正在执行/排队的任务，工作流节点里有 `ckpt_name` / `unet_name`；
- `GET /history?max_items=1` —— 最近一次完成的任务，同样带权重名。

实现：先查 `/queue`（有 ⇒ 显示「ComfyUI · 权重名」并注明「队列里的任务用的就是它」），
队列空再退到 `/history`（注明「最近一次任务用的它（队列空）」），
深度遍历节点时优先 `ckpt_name` / `unet_name`，其次 `diffusion_model` / `model_name` / `gguf_name`；
**LoRA 名与 VAE 名不当主模型**。文件名去掉 `.safetensors` 等后缀再显示。

实测（2026-10-20 21:30，用户正在跑 Qwen-Image 2.1）：

```
ComfyUI · qwen_image_2.1_bf16　正在运行　42.93 GB　｜ pid 72321 · 端口 8188 · 队列里的任务用的就是它
```

### 内存归因

- 用 `ri_phys_footprint`（活动监视器口径）。**实测 ComfyUI：`ps` 报 62 MB，phys_footprint 报 59.29 GB**
  —— 又一个「ps 少报一两个数量级」的实证，比 v3.1 记的 Python 23 GB 更极端；
- 一个进程托管多个模型时无法拆分 ⇒ 行尾标 `*`，脚注写明「内存是进程合计」，不假装知道各占多少；
- **引擎重启 / 互斥切换的过渡态**：同一引擎可能同时存在「已在本端口服务的实例」和「还没端口、正在退出的旧实例」。
  第一版会把旧的当成「应用内模型」重复列一行（实测出现过 `oMLX 37 GB` 与 `Qwen3.8-27B 19 GB` 并列）。
  现在把无端口同引擎实例的内存并到在服务的那一行，note 里注明「另含 N 个退出中的旧实例内存」—— 不丢账，也不重复占行。

### 布局自适应

模型通常只有 1–2 个，固定 4 行会留一大片空白。`applyModelLayout(rowCount:)` 按实际行数把窗口收短：
顶部区整体上移 `(4 - 行数) × 24`，下方三段榜与按钮坐标不动，窗口高度同步减少。
只保留用到的行，多余的隐藏。

**高度必须从基准帧算，不能在当前帧上做增量（v4.1 修）**：
第一版写的是 `f.size.height -= dy; f.origin.y += dy`，行数在 1↔2 之间来回变时高度只减不加，
几轮之后窗口被削到只剩下半截 —— 用户截图里「上面全没了、只剩 CPU 榜」就是这么来的。
现在改成：建窗时记下 `baseFrame`，每次 `目标高度 = baseFrame.height − dy`，顶边位置保持不动。

## 7. 性能与降本过程（实测）

| 版本 | 改动 | 自身 CPU | RSS |
|---|---|---|---|
| v0 | 512px 图标，4 Hz 重绘，无阈值 | **11.4%** | 105 MB |
| v1 | 256px 图标 + 2 Hz 重绘 | 5.4% | 88 MB |
| v2 | 叠加「整数百分比变化才重绘」+ GPU 采样 2 s | 1.8%（0.73 s / 40 s） | 87 MB |
| v2.1 | 菜单栏默认关闭（不再每秒重排 `NSAttributedString`） | **0.67%**（0.20 s / 30 s） | 93 MB |
| v4 | 加「本机 AI 模型」一栏（4 秒一采）+ 窗口加宽到 460 | 窗口开 **2.3%**（0.92 s / 40 s）｜窗口关 **1.5%**（0.68 s / 45 s） | 96 MB |

结论：这类工具的 CPU 成本几乎全在**不必要的重绘**。显示的是整数百分比，小数位抖动重绘纯属浪费。

`ioreg` 子进程实测单次仅 **10 ms**，按 2 s 一次计约 0.5%，不是瓶颈（故保留子进程方案，不引入 IOKit C 绑定复杂度）。

**进程榜零常驻代价**：`ProcessSampler` 只由窗口自己的 2 s 定时器驱动，窗口关闭即停（`windowWillClose`）。空载时不跑 `ps`、不读 ioreg。

## 8. 验收记录（全部实测）

**数值真实性**（压力对照，同一工具采样）：

| 场景 | CPU | GPU | MEM |
|---|---|---|---|
| 空载 | 8.8% | 0.0% | 22.0% |
| GPU 压力 + 30 路 `yes` | 96.1% | 83.0% | 22.3% |
| 仅留 GPU 压力 | 10.3% | 91.0% | 22.2% |
| 全停 | 7.6% | 0.0% | 21.9% |
| +26 GB 内存压占 | — | 80.0% | 38.7% |

三项读数均随真实负载同向变化 ⇒ 采样链路可信。

**成图验收**（`--dump` 导出 PNG → 视觉核对）：
- 布局「上二下一」；C/G 水印压在数字后，下排 `M xx%` 前缀；
- 高负载 `96/81/39`：CPU、GPU 转红，MEM 保持绿；
- 边界态 `100/100/100`：三位数完整在格内、进度条填满、不压边框；

## 9. 踩过的坑

1. **`lsappinfo info -only ... -app X` 返回 `[NULL]` + `!cgsConnection` 是误读。**
   该查询匹配不上时字段全 NULL，`!cgsConnection` 只是「未取到连接状态」，不代表进程没连 WindowServer。
   可靠判据是 `System Events` 的 `background only is false` 列表。
2. **`screencapture` 在本 agent 会话内不可用**（TCC 屏幕录制权限）。
   验收改走 `--dump` 导出图标 PNG——像素直接来自绘制代码，反而是更硬的证据。
3. **`swiftc` 里 `makeLibrary(source:options:)` 的 `options` 不能传 `[]`**，要 `MTLCompileOptions()`（写 GPU 压测程序时踩到）。
4. **LaunchAgent 必须 `LimitLoadToSessionType = Aqua`**，否则进程起在非图形会话，Dock 图标不出现。
5. **`NSImage(size:flipped:drawingHandler:)` 是延迟绘制**：真正光栅化时才执行，handler 里不要读会变化的全局值，一律传参数快照。
6. **水印字母不能贪大**：字号 1.34× 格高时文本框约 1.6 倍高，上下各被裁 30%，`C` 看起来像 `O`；1.0× 时轮廓完整。
7. **`ps -o comm=` 给的是完整路径**，显示前要取 `lastPathComponent`。
8. **别用 `active_count` 当已用内存**——它混着几十 GB 的文件缓存，会虚高 20 GB 以上（见第 4 节）。
9. **别信 `IOAccelerator` 的 `Device Utilization %`**——会假报 0（见第 4 节）。
10. **进程榜的 RSS 加起来远小于系统总占用是正常的**：大头在「压缩内存」与「内核 wired」，
    这两项不归属任何进程的 RSS。窗口里必须把内存去向拆开显示，否则用户一定质疑。
11. **窗口里文字过长会被截断**：419/420 宽放不下「内存分解」全串与「退出 Dockolate」按钮，
    实测截图里尾巴被吃。v4 窗口加宽到 460 + 文案缩短（`内存去向：文件缓存…（可回收）` → `内存分解：… 缓存…`），
    并为三段榜留出 310 pt 的进程名列。改完必须再截一次图核对。
12. **macOS 27 内核的 `struct socket_info` 比 SDK 头文件大 24 字节（792 vs 768）。**
    `proc_pidfdinfo(PROC_PIDFDSOCKETINFO)` 按内核布局写回，直接用 SDK 结构体 cast 会整体错位：
    实测读出的 `soi_kind = 0`、`soi_family = 1692183684`（垃圾），于是「监听端口」永远是空。
    正解：拿返回字节数减去 `MemoryLayout<socket_info>.size` 得到位移，再用**字节偏移**读
    `soi_kind@232`、`soi_family@160`、`tcpsi_state@320`、`insi_lport@244`（含位移），并做双重校验。
13. **不要靠进程名/argv 认 ComfyUI。** 它的进程名是 `Python`、argv 只有 `main.py --listen 127.0.0.1 --port 8188`，
    名字与参数里都没有 "comfy"。要么读 cwd，要么按**端口 8188** 认（本工具采用后者）。
14. **「假 resident」会骗人**：网关的 `resident` 只代表配置层认知，服务崩了仍可能是 true。
    所以故障判据必须是「声明常驻 + 端口真的连不上」，不能只看网关。
15. **LaunchAgent 常驻 + 用户双击/`open` 会起第二份实例**，两份都在画 Dock 图标、各开一个窗口。
    入口处做了单实例判断：后启动的那份 `activate` 先启动的、自己 `exit(0)`
    （plist 的 `KeepAlive.SuccessfulExit=false` 只对非零退出生效，正常退出不会被拉起来）。
    **但用 pid 比较会输给竞态**：登录时 LaunchAgent 的 `RunAtLoad` 与 Dock 的"登录恢复"
    几乎同一秒拉起两份，各自用 `runningApplications` 查对方时都可能还查不到，于是两份都活下来
    （实测 ppid 都是 1、同一秒启动、两个 Dock 图标）。改成 **`flock` 文件锁**：
    `~/Library/Application Support/Dockolate/instance.lock`，谁先拿到谁活，后到的激活前者再退出。
    并发拉起两份实测只剩一份。
16. **`screencapture -R x,y,w,h` 截到的是屏幕区域，被遮挡就截到别人的窗口**；
    截自己的窗口用 `screencapture -l<windowNumber>`（连写，中间不能有空格，否则只截到 60×86 的小图）。
    windowNumber 从 `CGWindowListCopyWindowInfo` 取。
17. **自适应尺寸一律「从基准值算」，绝不在当前值上做增量**：`height -= dy` 在 dy 反复变化时不可逆，
    窗口会一轮比一轮矮，最后顶部内容全被裁掉（本工具 v4 第一版就这么自毁了）。
    正解：记下建窗时的 `baseFrame`，每次 `目标值 = base − 偏移`，并保持顶边不动。

## 11. 开源化：通用引擎探测与双显示面（v5）

要公开分享，就不能只认自己那台机器。v4 的模型清单读的是本机 oMLX 网关
`127.0.0.1:8010/v1/models` 的 `local.resident` 私有字段 —— 别人的电脑没有这东西。
v5 整个换掉：

### 11.1 探测改成「端口 → 各家原生 API」

| 引擎 | 端口 | 取当前模型 |
|---|---|---|
| Ollama | 11434 | `/api/ps`；再 `/api/tags` 求差集 ⇒ **已下载未加载** |
| LM Studio | 1234 | `/api/v0/models` 的 `state == "loaded"` |
| llama.cpp | 8080/8081/8082 | `/v1/models`，兜底 `--model` argv |
| vLLM / MLX / oMLX | 8000/8001 | `/v1/models` |
| ComfyUI | 8188/8189 | `/queue` → `/history` 的 `ckpt_name` |
| A1111 / Forge / Draw Things | 7860/7861 | `/sdapi/v1/options` 的 `sd_model_checkpoint` |
| Fooocus / InvokeAI / KoboldCpp / TGWebUI | 8888/9090/5001/5000 | `/v1/models` |

- **零配置**：内置端口表，装什么认什么；`engines.json` 可加端口与 API key；
- **鉴权**：需要 key 的引擎（oMLX 无 key 一律 401）拿不到模型名时显示引擎名 + 端口，不猜；
- **去掉了"网关声明"这一路**：原来靠它判"该常驻却没在"，现在故障口径改为
  「进程占着端口但端口不应答」，不依赖任何一方的自我声明。

### 11.2 探测必须在后台跑

15 个端口 × 每家 4–5 个 API 试探，最坏能到秒级。原来在窗口定时器里同步跑，
一旦撞上慢端口就会卡住窗口。现在整段丢到独立 `DispatchQueue`，主线程只渲染缓存；
探测期间 UI 继续显示上一次结果，完成后回调刷新。

### 11.3 两个显示面各自开关

`UserDefaults` 的 `showDockIcon` / `showMenuBar` 两个键，窗口左下角两个勾选框，
状态栏菜单里同名的两个菜单项也同步。四种组合都允许（含"两个都关，只看窗口"）。
菜单栏读数沿用 v2 的紧凑风格：`C12 G40 M63`，字母按占用率变色。

## 13. 可发现性：搜索引擎为什么搜不到（2026-10-21 实测）

用户反馈「搜索引擎搜不到 dockolate，希望分享给别人时能被搜到」。以下为实测记录。

### 13.1 实测（时间 2026-10-21 19:10 CST）

| 通道 | 查法 | 结果 | 判读 |
|---|---|---|---|
| GitHub 站内仓库搜索 | `GET /search/repositories?q=dockolate` | `total_count = 1`（autugit/dockolate） | **已可搜到** |
| GitHub 站内精确限定 | `q=repo:autugit/dockolate` | `total_count = 1` | 已可搜到 |
| GitHub **代码**搜索 | `GET /search/code?q=README repo:autugit/dockolate` | `0` | 代码索引未建立 |
| 代码搜索对照组 | `q=fn+main repo:BurntSushi/ripgrep` | `28` | 说明 0 不是接口问题，是本仓未入索引 |
| 网页搜索引擎 | 查 `dockolate` | 10 条全是 Docklet / DockMate / Mockolate / DockTail | **未收录** |
| 仓库页可抓性 | `curl github.com/autugit/dockolate` | `200`，无 `robots: noindex`，`<title>` / `og:description` 正常 | 未被主动屏蔽，只是没被发现 |
| 仓库首页字段 | `gh repo view --json homepageUrl` | 空 | 没有从站外指向仓库的入口 |
| GitHub Pages | `GET /repos/.../pages` | `404` | 未启用，没有独立落地页 |
| 仓库年龄 / 社交信号 | API | 建于 2026-10-20T14:47:29Z，21 commits，0 star、0 fork | 约 20 小时、零外链 |

### 13.2 结论（为什么搜不到）

1. **仓库只有 20 小时历史，且零外链。** 搜索引擎发现新页面的路径是「别的已被抓取的
   页面链到它」，从不是「主动扫描 GitHub 全站」。GitHub 没有公开的全量仓库 sitemap，
   0 star / 0 外链的新仓库在 Google 侧常见是数周起步，也常有长期不收录的情况。
   Bing 直抓在本机被反爬降级（返回无关的沙龙、二手车结果），不能当判据，故只用
   可复现的搜索接口结论。
2. **GitHub 的代码搜索与仓库搜索是两套索引。** 仓库页已可搜，代码搜索仍为 0
   （对照组 28 证明对照有效），所以「在 GitHub 搜 dockolate 搜不到」若发生在
   code 搜索页签，是索引时延，不是仓库不可见。
3. **名称撞词严重。** Docklet / DockMate / Mockolate / DockTail / DockLite 占满了
   `dockolate` 附近的自然结果位，即便被收录，裸品牌词也很难排上去；真正能排的是
